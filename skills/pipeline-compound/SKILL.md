# Pipeline Compound：知识沉淀

## 概述

读取本工单全套工件，把值得留下的知识**按去向分拣**后落盘。沉淀的价值判据只有一个：**下一个工单（或下一个会话）会因为这条记录少走弯路吗？** 不满足的不写——复述流水账是最常见的沉淀失败。

**开始前必读**：`${CLAUDE_PLUGIN_ROOT}/skills/_shared/handoff-spec.md`。

**参数**：工单 ID。**输入**：`docs/pipeline/<ticket-id>/` 全部工件 + `git log` 中本工单的提交记录；`05-knowledge-hints.md` 存在时先读——里面是知识库既有条目，**同一条知识沿用既有标题更新，不要换个说法新增**（标题是知识去重的键）。**工具边界**：Read/Grep/Glob/Bash（读历史）+ Write（仅写本阶段四个产物）。**不直接修改 CLAUDE.md 或任何 skill**——CLAUDE.md 建议写进 `92-suggestions.json`，编排器发人审卡，采纳后自动合入。

## 素材挖掘（按信息密度排序）

1. **修复回环记录**（ledger 的 fix round 行、40-acceptance 的多轮回填）：每次打回都是一条"某个环节的预防措施缺失"的证据。追问：这个问题本可以在哪个更早的阶段被拦住？
2. **各工件的"失败过的尝试"与"事实 vs 假设"**：已验证的环境限制（如工具链跑不了某类测试）、被推翻的假设。
3. **review/acceptance 发现的既有缺口**（非本次引入的问题）：候选新工单。
4. **概念纠正**：需求原文与最终实现之间的理解差（如"新增功能"实为"补前端入口"）。

## 三路分拣（每条素材过一遍判据）

| 去向 | 判据 | 产出形式 |
|---|---|---|
| **目标仓库 CLAUDE.md** | 项目常识：下次**任何**会话进这个仓库都该知道（构建怪癖、环境限制、领域规则、部署形态差异） | 结构化条目写入 `92-suggestions.json` 的 `claudeMd`（编排器发人审卡，采纳后自动合入并提交） |
| **pipeline plugin（流程）** | 跨仓库、跨工单的流程改进（某阶段该多查什么、验证方式怎么写才可判定） | 结构化条目写入 `92-suggestions.json` 的 `process`（编排器转发给人，人工改 skill）；证据与展开说明写 `90-retro.md` |
| **叙事复盘（Wiki）** | 给人看的一次性复盘：本单为什么回环、教训是什么 | `90-retro.md` 正文（编排器负责 `move_docs_to_wiki` 归档） |

分拣纪律：
- **CLAUDE.md 是稀缺资源**：每条建议 ≤2 行、必须可执行（"注意 X"不合格，"X 时用 Y"合格）；本单特有的信息不进 CLAUDE.md。
- 同一条素材可以多路（环境限制既进 CLAUDE.md 一行，也进流程建议）。
- 无可沉淀内容的路写"无"——硬凑比空白更有害。

## 产物一：95-delivery.md（交付文档，给人读的总览）

把全套工件编译成**一份能从头读到尾**的开发文档——业务方与半年后来查"这功能当初为什么这么设计"的人只会读这一份。编排器会把它推成飞书云文档并归档进知识库，所以：**只写事实，不写过程流水账；每个结论都能在工件里找到出处**。

固定结构（缺的部分写"无"，不要省略小节）：

```markdown
# <工单号> <一句话标题>

> 本文档由流水线自动生成，权威源是仓库 `docs/pipeline/<工单号>/` 下的工件；正文修改请回到 git。

## 结论
[3-5 句：做了什么、验收结果、有没有遗留]

## 需求与验收标准
[需求原文要点 + 需求变更（若有）+ AC 清单表格：编号/描述/验证方式/验收结果]

## 方案与关键决策
[技术方案要点；每条关键决策写清"选了什么、为什么、放弃了什么"；被审批驳回过的方案也要写]

## 执行过程
[任务清单与结果；回环记录：第几轮、因为什么被打回、怎么修的；引用评审 findings]

## 验收结果
[逐条 AC 的结果与证据（命令输出摘要 / 人工确认）；无法验证项与待补验说明]

## 遗留与后续
[已知问题、park 的 findings、建议另开的工单]

## 成本与耗时
[各阶段会话数/成本/回环次数汇总表]
```

## 产物二：96-knowledge.json（知识条目，给下一单读的）

把可复用的经验写成结构化条目——这些会进知识库，**并在未来工单的澄清/计划阶段被自动预取**。所以每条都要写到"下一个人不看原工单也能用"。

```json
[
  {
    "title": "反向代理新增暴露路径必须同步三份 nginx 配置",
    "kind": "踩坑",
    "scope": "本项目",
    "tags": ["nginx", "部署", "反向代理"],
    "symptom": "新端点在本地可用，部署后请求落回前端 SPA 页面",
    "cause": "仓库有三份代理配置（dev proxy + 两份容器 nginx.conf），只改了其中一份",
    "practice": "凡新增对外暴露的 HTTP 路径，先列全仓库所有代理配置文件，逐一确认转发规则",
    "evidence": "docs/pipeline/LS-003/25-impl-report.md"
  }
]
```

字段规则：

- `kind` 取 `踩坑` / `项目常识` / `流程改进` / `决策先例` 之一。
- **`scope` 决定这条经验会不会喂给别的项目**，取值：
  - `本项目`——只在这个代码库成立（"本仓库有三份 nginx 配置"）
  - `技术栈`——用同样框架/库的项目都该知道（"GORM 的 default tag 会让 Go 零值被列默认值替换"）
  - `执行环境`——同一台执行机上所有项目都适用（"本机 Docker daemon 通常未运行"）
  - `流程`——与代码无关的流水线经验（"验收不通过必须附失败现象"）
  
  **判据：换一个代码库，这条还成立吗？** 成立就不是 `本项目`。标错成 `本项目` 会让通用经验困死在一个仓库里；标错成通用则会污染别的项目的提示。
- `title` 是**同一条知识的稳定标识**（同标题会被更新而不是新增，所以命名要概括性、不要带工单号）。
- 没有可沉淀的经验时写 `[]`，**不要为了凑数编条目**。

## 产物三：92-suggestions.json（建议，编排器发人审卡）

CLAUDE.md 建议与流程改进建议的**结构化真源**。编排器读它发飞书人审卡：`claudeMd` 条目被采纳后**自动追加进目标仓库 CLAUDE.md 并提交**，所以每条必须独立成立、可直接入文；`process` 条目转发给人（不自动执行）。

```json
{
  "claudeMd": [
    {
      "section": "## 环境限制",
      "line": "- 本机 Docker daemon 通常未运行；nginx 配置验证用 docker/check-nginx-mcp-limits.sh，不要跑 nginx -t",
      "why": "该限制在 implement/review/acceptance 各阶段被独立重复发现（见 90-retro.md 工单数据）"
    }
  ],
  "process": [
    { "skill": "pipeline-acceptance", "suggestion": "验收「不通过」必须附失败现象自由文本" }
  ]
}
```

字段规则：

- `section`：CLAUDE.md 的目标小节标题（含 `#` 前缀）。优先复用 CLAUDE.md 现有小节；不存在的小节会在文件末尾新建。
- `line`：要追加的完整一行（含 `- ` 等格式），**单行、可执行**（"X 时用 Y"合格，"注意 X"不合格）；与 CLAUDE.md 中完全相同的行会被跳过，所以措辞要稳定。
- `why`：触发本建议的证据，渲染进人审卡片——人只看卡片就能决策。
- 无建议时写 `{"claudeMd": [], "process": []}`，不要省略文件。
- **提出前先查重**：读目标仓库 CLAUDE.md，已覆盖的常识不重复建议；上一单提过且被驳回的建议（见 90-retro/feedback 记录）不原样重提。

## 结束

按 handoff-spec §6 自查后输出结构化返回，`handoff_path` 指向 `90-retro.md`。`summary_for_card` 面向团队：本单核心教训 + 几条建议待人审。本阶段固定 `status: DONE`（沉淀没有打回一说；素材不足就少写）。

**四个产物都要写**：`95-delivery.md`（给人读的总览）、`96-knowledge.json`（给下一单读的条目）、`92-suggestions.json`（建议真源，编排器发人审卡）、`90-retro.md`（复盘与展开说明）。少写任何一个都算本阶段未完成。
