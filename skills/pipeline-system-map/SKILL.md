# Pipeline System Map：系统能力地图

## 概述

产出并维护 `docs/pipeline/system-map/`——**让一个零上下文的会话（或一个不懂实现的业务人员）读完就知道这个系统能做什么、每件事在哪、还缺什么**。

它服务于一个具体场景：业务人员给出一句模糊需求时，澄清阶段能立刻判断"这落在既有能力 X 上，是要扩展它还是新建"，而不是从零 Grep 一遍代码再猜。

**开始前必读**：`${PIPELINE_PLUGIN_ROOT}/skills/_shared/handoff-spec.md`。

**参数**：`rebuild`（全量重建）或 `ticket=<工单号>`（增量更新）。

## 与 PROJECT-BRIEF 的分工（不许复述）

| 文件 | 回答的问题 | 典型内容 |
|---|---|---|
| `PROJECT-BRIEF.md` | 这个系统**是什么** | 领域对象与关系、部署形态、历史决策与教训 |
| `system-map/` | 这个系统**能做什么、在哪、还缺什么** | 能力清单、每个能力的入口与边界、未决问题与债 |

同一条事实只写一处。地图需要用到领域概念时**链接** PROJECT-BRIEF，不重写定义——两处各写一份必然漂移。

## 一条能力是什么

能力 = **业务人员会说出口的一件事**，不是代码模块。判据：能力的名字里不出现技术词（"用户管理"合格，"UserService 层"不合格），且业务人员看到这个名字知道自己要的是不是它。

粒度判据：一个能力对应一组用户能连续完成的操作（通常 1 个前端页面域 + 支撑它的接口组），全系统的能力数落在 5–20 之间。超过 20 说明切碎了，少于 5 说明混在一起。

## 产物

### index.md（唯一入口，≤120 行）

```markdown
# <系统名> 能力地图

> 生成于 <ISO 时间> · 代码基线 `<短 sha>` · 由流水线 pipeline-system-map 维护。
> 这是索引不是仓库：每条只给一句话，细节在各自的能力页里。
> 系统背景（领域对象、约束、历史决策）见 [PROJECT-BRIEF](../PROJECT-BRIEF.md)。

| 能力 | 一句话用途 | 谁能用 | 详情 |
|---|---|---|---|
| <业务语言的能力名> | <这个能力让人完成什么> | <角色：全体登录用户/工作空间管理员/系统管理员/外部客户端> | [详情](capabilities/<slug>.md) |

## 尚不清楚的部分
```

### capabilities/<slug>.md（每个能力一份，≤80 行）

```markdown
# <能力名>

**用途**：<业务人员视角，2-3 句：谁在什么场景下用它、解决什么问题>
**谁能用**：<角色 + 鉴权强度（路由级中间件链）>
**状态**：<可用 / 部分可用（说明缺什么）/ 已废弃（说明替代者）>

## 入口

| 类型 | 位置 | 说明 |
|---|---|---|
| 页面 | `frontend/src/pages/...` | <用户从哪进> |
| 接口 | `<方法> <路径>` (`router.go:<行>`) | <做什么> |

## 涉及的领域对象

<链接 PROJECT-BRIEF 中的定义，只写本能力特有的补充事实>

## 边界与已知问题

<这个能力明确不做什么；已知缺陷与债，注明来源工单>

## 相关工单

<工单号 + 一句话：它给这个能力带来了什么>
```

### map.json（机器可读，编排器算新鲜度用）

```json
{
  "version": 1,
  "generated_at": "<ISO 时间>",
  "code_commit": "<生成时的 HEAD 完整 sha>",
  "capabilities": [
    {
      "slug": "<文件名>",
      "title": "<能力名>",
      "paths": ["backend/internal/handler/xxx.go", "frontend/src/pages/Xxx"],
      "lastTicket": "<最后改动它的工单号>"
    }
  ]
}
```

`paths` 是新鲜度判据的依据——编排器用它判断某个能力的代码是否在地图生成后被改过，所以**只填该能力的核心实现路径**（3–8 条），不要把整个仓库列进去。

## 全量重建（参数 `rebuild`）

1. **取基线**：`git rev-parse HEAD` 记下完整 sha，写进 `map.json.code_commit`。
2. **枚举入口**（能力的证据来自入口，不是目录结构）：路由注册处（含每组的中间件链，它决定"谁能用"）、前端路由配置与页面目录、对外协议入口（如 MCP 工具注册）、定时任务注册处。**判据**：每一条路由与每一个前端页面都被归入某个能力或显式记入"尚不清楚的部分"，无一遗漏——按清单逐条核销，不凭印象。
3. **读工单历史**：`docs/pipeline/*/95-delivery.md` 的「结论」与「遗留与后续」、`PROJECT-BRIEF.md`。这是业务意图的来源；只读代码写不出"这个能力是给谁用的"。
4. **归并成能力**（按上面的粒度判据），逐个写 `capabilities/<slug>.md`。
5. **汇总** `index.md` 与 `map.json`。未决清单从各工单的「遗留与后续」+ 评审 park 的 findings 汇总。
6. **自查**：能力数在 5–20；每条能力名不含技术词；每个 `paths` 里的文件都真实存在（逐个 Read 确认，写错路径的地图比没有地图更浪费下游时间）。

## 增量更新（参数 `ticket=<工单号>`）

只改动本工单触及的部分，**不重写整张地图**（重写会把上一轮人工修正冲掉）：

1. 读该工单的 `95-delivery.md`（结论、AC 清单、遗留与后续）与 `25-impl-report.md`。
2. 判断本单是：**扩展了既有能力**（改对应能力页）／**新增了能力**（新建能力页 + index 加一行）／**只是修复**（通常只更新该能力页的"已知问题"与"相关工单"）。
3. 把本单的「遗留与后续」中未解决项并入 index 的未决清单，注明来源工单。已被本单解决的旧条目**删掉**（未决清单只留还欠着的）。
4. `map.json`：更新受影响能力的 `paths` 与 `lastTicket`；`code_commit` 更新为本单合入后的 HEAD。
5. **不做全量核销**——增量轮不负责发现地图里其他部分的漂移，那是 `rebuild` 的职责。

## 结束

按 handoff-spec §6 自查后输出结构化返回，`handoff_path` 指向 `docs/pipeline/system-map/index.md`。

`summary_for_card` 写给团队：本次是重建还是增量、能力清单有什么变化、未决清单增减几条。

状态出口：写完全部产物 → `DONE`；仓库结构无法识别入口（既找不到路由也找不到页面）→ `BLOCKED` 并说明找了哪些位置。
