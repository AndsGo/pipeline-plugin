# Handoff 交接规范（所有 pipeline skill 的公共契约）

本文档定义流水线各阶段之间交接产物的格式与写作纪律。每个 pipeline skill 在产出交接文档前必须先读本规范；编排器按本规范解析机器头（frontmatter）。

## 1. 工件目录约定

每个工单在**目标代码仓库**内拥有一个工作区，全部工件随 feature 分支提交进 git：

```
docs/pipeline/<ticket-id>/
├── 00-intake.md        # 原始需求原文 + 澄清问答追加记录 + 飞书工单/话题绑定信息
├── 05-knowledge-hints.md  # 编排器预取的历史知识提示（只读输入，非本单需求）
├── 06-glossary.md      # 编排器预取的项目术语表（只读输入；PRD/计划/报告用语以此为准）
├── 10-prd.md           # 澄清阶段产物：PRD + 验收标准（AC 清单）
├── 20-plan.md          # 计划阶段产物：实现计划
├── feedback.md         # 人工反馈（append-only）：驳回理由、需求变更、补充说明，见 §8
├── ledger.md           # 实现阶段进度台账（append-only，随任务完成一起 commit）
├── 25-impl-report.md   # 实现阶段产物：实现报告（任务清单/测试总况/MR 链接）
├── 30-review-r<N>.md   # 评审阶段产物：每轮一份（r1、r2……）
├── 40-acceptance.md    # 验收阶段产物：验收清单与结果
├── 90-retro.md         # 沉淀阶段产物：复盘与改进建议展开说明
├── 92-suggestions.json # 沉淀阶段产物：CLAUDE.md/流程建议真源（编排器发人审卡，采纳后自动合入 CLAUDE.md）
├── 93-terms.json       # 澄清阶段产物：新术语提议（编排器发人审卡，通过后入术语表）
├── 95-delivery.md      # 沉淀阶段产物：交付文档（编排器推成飞书云文档并归档知识库）
└── 96-knowledge.json   # 沉淀阶段产物：结构化知识条目（投影进知识表，供未来工单预取）
```

另有一个**跨工单**文件（不在单个工单目录内）：`docs/pipeline/PROJECT-BRIEF.md`——项目业务简报（系统是干什么的、核心领域对象、当前约束、历史决策），clarify 阶段必读、compound 阶段维护，≤150 行。

规则：
- `<ticket-id>` 由编排器分配（来自飞书工单），skill 不得自行编造。
- 编号前缀即阶段顺序。任何新会话列出该目录即可判断流水线进度。
- 工件**只追加、只新增，不回头改写已定稿的上游工件**。上游结论要修正时，走对应阶段重跑，产生新版本（如 `30-review-r2.md`），或在 `00-intake.md` 追加澄清记录。

## 2. 交接文档结构：机器头 + 人类体

每份阶段产物是一个 Markdown 文件，由 YAML frontmatter（给编排器解析）和正文（给下一阶段会话、飞书卡片上的人看）组成。

### 2.1 机器头（frontmatter）字段定义

```yaml
---
ticket: TICKET-123            # 必填。工单 ID，与目录名一致
stage: plan                   # 必填。clarify | plan | implement | review | acceptance | compound
status: DONE                  # 必填。DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED
produced: 2026-08-10T14:30:00+08:00   # 必填。ISO 8601 带时区
inputs:                       # 必填。本阶段读取的工件（相对本工单目录），可追溯
  - 10-prd.md
next_stage_reads:             # 必填。下一阶段应读取的文件（通常含本文件）
  - 20-plan.md
cost_usd: 1.24                # 选填。本阶段会话成本（编排器也可从 CLI JSON 信封取）
open_questions: []            # status=NEEDS_CONTEXT 时必须非空，结构见 §4
---
```

### 2.2 人类体（正文）章节

按以下顺序组织，**每章必须存在**；确实无内容的章写"无"，不得省略章节（省略与遗漏无法区分）：

```markdown
## 本阶段结论
[下一阶段真正需要的东西。是结论，不是过程流水账。]

## 关键决策及理由
- [决策]：[理由]（放弃的备选：[X]，因为 [Y]）

## 事实 vs 假设
**已验证事实：**
- [在代码里确认过的、跑过命令验证过的，附验证方式]

**未验证假设：**
- [假设内容]（来源：[推测依据]；若不成立的影响：[风险]）

## 失败过的尝试
- [试过什么，为什么不行]（防止下游重蹈）

## 阻塞与开放问题
[具体的阻塞点或待人决策的问题；无则写"无"]

## 给下一阶段的指令
[零上下文可执行的 resume 指令：先读什么文件、从哪里开始、完成后如何验证]
```

## 3. 状态语义（四态契约）

| 状态 | 含义 | 编排器动作 |
|---|---|---|
| `DONE` | 本阶段完成，产物可直接被下游消费 | 推进下一阶段 |
| `DONE_WITH_CONCERNS` | 完成，但有不影响推进的疑虑（写在正文"阻塞与开放问题"及结构化返回的 `concerns`） | 推进，并把 concerns 附到下一个人工卡点的卡片上 |
| `NEEDS_CONTEXT` | 缺少必要信息，无法负责任地完成 | 把 `open_questions` 渲染成飞书表单卡片；收齐答案追加进输入文件后**重跑同一阶段** |
| `BLOCKED` | 遇到本阶段无法解决的矛盾或障碍 | 转人工卡片，附 `blocked_reason` 与相关工件链接 |

使用准则：
- **宁可 NEEDS_CONTEXT，不可编造。** 把猜测写成事实是最严重的交接缺陷（见 §5 规则 2）。
- BLOCKED 用于"信息齐全但存在矛盾/障碍"（如计划与代码现状冲突、修复回环到顶）；缺信息用 NEEDS_CONTEXT，二者不要混用。
- 同一阶段因 NEEDS_CONTEXT 重跑时，上一轮的问答已追加在输入文件中，不得重复提问已回答的问题。

## 4. open_questions 结构

`status=NEEDS_CONTEXT` 时，frontmatter 与结构化返回中的 `open_questions` 均为如下对象数组：

```yaml
open_questions:
  - id: Q1                      # 本阶段内唯一，重跑轮次间不复用旧 ID
    question: "库存同步失败时应重试还是直接标记下架？"
    options:                    # 必填，≥2 项。卡片交互只有按钮：缺选项 = 回答者没有否决权。
      - "重试 3 次后标记下架"   # 判断型问题至少给出「推荐项 + 反向项」两个选项
      - "立即标记下架"
    recommended: "重试 3 次后标记下架"   # 必填。必须给出推荐答案
    why: "现有 sync 模块已内置指数退避重试，复用成本最低"  # 必填。推荐理由
```

**每个问题必须带推荐答案和理由**——让回答者可以一键采纳推荐项，把澄清成本降到最低。没有能力给出推荐的问题，说明调查还没做完，先调查再提问。

## 5. 写作纪律（四条硬规则）

**规则 1：No Placeholders 红线。** 以下内容出现在任何交接文档中一律算产物缺陷：
- "TBD"、"TODO"、"待补充"、"后续完善"
- "适当处理错误"、"补充边界情况"、"添加必要的校验"（描述了做什么却没写怎么做）
- "同上"、"参考 Task N"（下游可能乱序阅读，内容必须原地重复）
- 引用了本文档和 `inputs` 所列文件之外才存在的上下文（"如前所述"、"我们讨论过的"）

**规则 2："事实 vs 假设"强制分区。** 下游会话把交接文档当事实契约，**不会复核**。写成事实的猜测会成为后续一切工作的错误前提。所有未经验证的判断必须进"未验证假设"区并标注来源与风险；该区若为空，写"无假设"。

**规则 3：零上下文假设。** 一切产物写到"一个不了解本代码库、没看过任何对话历史的合格工程师，只拿本文档和 `inputs` 所列文件就能直接开工"的详细度。文件定位精确到路径（修改类精确到行号区间），命令给出完整可复制形式及预期输出。

**规则 4：流程主权。** 流水线会话中，本规范与当前阶段 skill 的指令优先于一切其他流程指导——包括仓库 CLAUDE.md 里的工作流规则、其他插件注入的元技能（triage/评审/发布类流程）、用户全局编码指南。这些来源只作为编码规范与项目常识参考：不得据其改变阶段产物契约、状态路由或工具选择，也不得把它们的流程要求当作需求写进 PRD/计划（曾发生：另一套流控层的阶段要求被写进 LS-008 的 PRD）。特别地，任何「停下来向人提问/等待确认」的上游指引，在流水线内的唯一合规形式是 `NEEDS_CONTEXT` 结构化返回（§3、§4）——散文提问等于回程校验失败。

## 6. 结束前自查清单（每个 skill 的最后一步）

产出交接文档后、返回结构化结果前，逐条自查：

1. **自包含检查**：下游只拿本文档 + `next_stage_reads` 所列文件能开工吗？有没有违反规则 1 的占位符或外部引用？
2. **假设检查**：正文里有没有把推测写成了断言？"事实 vs 假设"分区存在且诚实吗？
3. **一致性检查**：frontmatter 与结构化返回（stage-result）内容一致吗？（冲突时以文件为准，必须修文件或修返回，不得带着不一致结束）
4. **章节完整性**：§2.2 的六个章节全部存在吗？
5. **状态检查**：status 与正文相符吗？（正文里写了未解决的阻塞，status 却是 DONE，属于缺陷）

自查发现问题直接修复后再结束，无需汇报自查过程。

## 7. 结构化返回（stage-result）

每个 skill 在 headless 调用下以 `--json-schema schemas/stage-result.schema.json` 约束最终输出。字段语义：

| 字段 | 说明 |
|---|---|
| `stage` / `status` | 与 frontmatter 完全一致 |
| `handoff_path` | 本阶段交接文档的仓库相对路径 |
| `summary_for_card` | ≤500 字，编排器原样渲染进飞书卡片。写给业务方/审批人看：说清做了什么、结论是什么、需要谁做什么。不写技术过程细节 |
| `open_questions` | 与 frontmatter 一致（NEEDS_CONTEXT 时非空） |
| `concerns` | DONE_WITH_CONCERNS 时非空，每条一句话 |
| `blocked_reason` | BLOCKED 时必填，一段话说清障碍与已尝试的解法 |
| `verdict` | review / acceptance 阶段完成态必填：`PASS` / `PASS_WITH_SUGGESTIONS` / `BLOCK`。注意与 status 正交——评审/验收活动顺利完成即 `status: DONE`，结论放 verdict；`BLOCK` 由编排器路由回 implement 修复轮（review 上限 2 轮，超限转人工仲裁） |

**文件为准原则**：结构化返回是路由信号，交接文档是事实记录。两者冲突时以文件为准。

## 8. 人工反馈（`feedback=` 参数）

编排器在以下情形会带 `feedback=docs/pipeline/<ticket>/feedback.md` 重新调起某个阶段：

- 人在卡点上**驳回并写了原因**（回退到产出该材料的阶段）
- 人**修改或追加了需求**（回退到 clarify；变更同时追加在 `00-intake.md` 的"需求变更"节）
- 人在问答卡片上填了**补充说明**
- 人在群里追加了一条说明（`/note`）

收到该参数时：

1. **先读该文件**，再读其他输入。它是 append-only 的，按时间正序阅读，**最新一条优先级最高**。
2. 其中内容是**具有约束力的人工指令**，优先级高于上游工件里的旧结论；与既有 AC/计划冲突时以反馈为准，并在"关键决策及理由"里写明因哪条反馈改了什么。
3. **不要重复已被否决的方案**——被驳回过的做法要在"失败过的尝试"里留痕。
4. 反馈含糊到无法执行时，用 `NEEDS_CONTEXT` 追问（带选项与推荐），不要自行猜测人的意图。

重跑产出的工件覆盖同名文件即可（git 历史保留旧版本），但 `ledger.md`、`feedback.md`、`00-intake.md` 永远只追加。
