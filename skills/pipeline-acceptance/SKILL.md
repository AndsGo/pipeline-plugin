# Pipeline Acceptance：验收

## 概述

把 `10-prd.md` 的 AC 清单变成验收结果：**自动项亲自运行验证命令并记录证据，人工项生成零上下文可执行的检查单交人完成**。验收的唯一依据是 AC 清单——不重新评审代码，不扩大范围。

**开始前必读**：`${CLAUDE_PLUGIN_ROOT}/skills/_shared/handoff-spec.md`。

**参数**：工单 ID。**输入**：`10-prd.md`（AC 清单）、最新一轮 `30-review-r<N>.md`（其"给下一阶段的指令"中的人工重点项必须并入检查单）、`25-impl-report.md`（了解 MR/部署状态与已知 concerns）；`05-knowledge-hints.md` 存在时先读——历史验收类踩坑（如某环境跑不了某类验证命令），据此把注定跑不了的自动项提前分流为人工项，而不是现场发现。输入缺失 → `BLOCKED`。
**项目流程约定**：`docs/pipeline/<ticket-id>/07-project-profile.md` 存在时**先读它**——那是本项目对本阶段的约定（测试环境有无与地址、验收人是谁、上线方式、项目特有的做法与禁忌），由编排器从仓库 `docs/pipeline/PIPELINE.md` 节选而来。与本 skill 的通用流程冲突时以它为准：项目事实优先于通用流程。

**工具边界**：Read/Grep/Glob/Bash（运行验证命令）+ Write/Edit（仅写 `40-acceptance.md`）。禁止修改任何业务代码——发现问题是打回，不是顺手修。

## 第一轮：自动项验证 + 人工检查单

1. 逐条读取 AC，按"验证方式"分流。
2. **自动项**：在工单分支的工作区（或编排器指明的部署环境）运行验证命令，逐条记录 `PASS` / `FAIL` + 命令 + 关键输出摘要。命令因环境缺失跑不了（依赖装不上、需要部署环境）→ 记 `无法自动验证`，降级为人工项并写明原因。
3. **任一自动项 FAIL → 立即 `verdict: BLOCK` 结束**（`status: DONE`，失败证据写进文档），不再发起人工验收——先修再验，不浪费验收人时间。命令能运行而断言失败（包括目标函数/文件不存在、实现与声称不符）**都算 FAIL 走 BLOCK**；`BLOCKED` 只用于输入工件缺失或命令因环境缺失根本无法运行。
4. 全部自动项通过 → 生成人工检查单，写入 `40-acceptance.md`（`status: NEEDS_CONTEXT`），`open_questions` 每条人工 AC 一项：
   - `question`：含 AC ID + 完整操作步骤 + 预期结果（从 PRD 原文带出，review 指令中的补充关注点并入步骤），末尾注明"选「不通过」请在补充说明里描述实际现象"
   - `options`：`["通过", "不通过", "无法验证"]`（「不通过」必须附失败现象——编排器会对缺现象的驳回强制追问）
   - `recommended`：写"通过（前提：实际操作结果与预期一致）"
   - `why`：引用支持性证据（相邻自动测试结论、review 判定），并明确"推荐不能替代实际操作"

   **检查单完成判据**：每条人工 AC 的步骤零上下文可执行（含入口路径/菜单位置与预期画面），且题干直接使用该 AC 的「业务验收描述」原文；做不到的项写明缺什么。

## 第二轮：汇总定稿（人工结果已由编排器追加进 40-acceptance.md）

- 已回答的项不重复提问；`无法验证` 项进 concerns（写明原因与建议的补验时机）。
- **复验模式**：若存在"不通过"项、且 ledger/25-impl-report 中有晚于该回填的修复记录，则仅对这些项重新生成检查单（问题中注明修复内容与复验前提，如"需重启 dev server"），进入新一轮 `NEEDS_CONTEXT`；已通过的项沿用原结果，不重新提问。
- **结论映射**：全部通过（或仅"无法验证"）→ `verdict: PASS`（有"无法验证"时 `status: DONE_WITH_CONCERNS`）；任何一条"不通过"→ `verdict: BLOCK`，把验收人描述的失败现象逐字记录到文档（这是修复轮最重要的输入，不要转述加工）。

## 产物：40-acceptance.md

frontmatter 按 handoff-spec（`stage: acceptance`，定稿轮加 `verdict:`），"本阶段结论"含 **AC 结果总表**：

```markdown
| AC | 类型 | 结果 | 证据 |
|---|---|---|---|
| AC-1 | 自动 | PASS | `pnpm test ...`：12 passed（输出摘要） |
| AC-2 | 人工 | 通过 | 验收人确认（第 2 轮问答） |
| AC-6 | 人工 | 无法验证 | 本环境无 MCP 客户端，建议上线后补验 |
```

"给下一阶段的指令"：PASS 时写给沉淀阶段（本单有哪些值得复盘的点：回环轮数、无法验证项、既有缺口发现）；BLOCK 时写给修复轮（失败 AC、验收人原话、复现步骤）。

## 结束

按 handoff-spec §6 自查后输出结构化返回。`summary_for_card` 面向业务方：验收结论、通过/不通过/待补验条数、下一步（合并上线或打回修复）。
