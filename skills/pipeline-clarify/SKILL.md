# Pipeline Clarify：需求澄清 + 验收标准

## 概述

把业务原始需求转化为两样东西：**PRD**（消除了歧义的需求描述）和**验收标准清单**（AC，每条都能被零上下文的验收人独立执行）。本阶段**只澄清"做什么"和"怎么算做完"，不设计"怎么做"**——实现方案是 pipeline-plan 的事，本阶段写了实现方案属于越界缺陷。

**开始前必读**：`${PIPELINE_PLUGIN_ROOT}/skills/_shared/handoff-spec.md`（交接格式、四态语义、写作纪律、自查清单，本文不重复其内容）。

**参数**：工单 ID。工作区为 `docs/pipeline/<ticket-id>/`。

**工具边界**：只读代码库（Read/Grep/Glob），唯一的写操作是产出本阶段工件。不运行修改状态的命令。

## 输入检查

读取 `docs/pipeline/<ticket-id>/00-intake.md`：

- 文件不存在 → `status: BLOCKED`，`blocked_reason` 写明"编排错误：00-intake.md 缺失"。不要自己创建它。
- 文件存在且含"## 澄清问答"追加记录 → 本次是**重跑轮**：已回答的问题视为定论，禁止重复提问；新问题的 ID 接续编号，不复用旧 ID。
- 文件写着"来自需求 REQ-xxx"（编排器从需求池转来的单）→ 里面的《需求说明》是提出人在梳理阶段确认过的：其中"## 澄清问答（需求梳理阶段…）"同样视为定论、不再重问；**"调研结论"里的事实是梳理会话查的，写 PRD 前逐条用代码核实**，核实不了的挪进"事实 vs 假设"的假设栏，不要整段照搬；本工单只负责它写明的那一项拆分，其余拆分项不进 In。
- 文件含"## 需求变更"节 → 需求已被人修改：**以最后一次变更为准**，PRD 与 AC 必须按新需求重写，被推翻的旧结论移入"失败过的尝试"。
- 调用参数含 `feedback=<path>` → 按 handoff-spec §8 先读该文件，把其中内容当作约束性人工指令。
- 工单目录存在 `05-knowledge-hints.md` → 先读它（历史工单沉淀的经验，由编排器预取）。**与本需求相关的条目要在 PRD 里显式采纳**（写进"事实 vs 假设"或 AC 的前提条件），明确不适用的在"关键决策及理由"里说明为何排除；无关的忽略。它是提示不是需求，不要把历史经验当成本单的要求。
**项目流程约定**：`docs/pipeline/<ticket-id>/07-project-profile.md` 存在时**先读它**——那是本项目对本阶段的约定（测试环境有无与地址、验收人是谁、上线方式、项目特有的做法与禁忌），由编排器从仓库 `docs/pipeline/PIPELINE.md` 节选而来。与本 skill 的通用流程冲突时以它为准：项目事实优先于通用流程。
- 工单目录存在 `06-glossary.md` → 先读它（项目术语表）。**PRD/AC 的业务名词必须使用其中的规范词**，出现禁用同义词算产物缺陷。
- 仓库存在 `docs/pipeline/system-map/index.md` → **先读它**（能力地图：系统能做什么、在哪、还缺什么）。它是唯一入口，自己指向 `PROJECT-BRIEF.md`（系统是什么）与各能力页——按需要往下读，不要一次全读。工单目录的 `07-map-hint.md` 是编排器算出的新鲜度（落后多少提交、哪些能力的代码已变动）：**落后不等于作废，但地图与代码冲突时以代码为准**，并把该冲突写进"事实 vs 假设"提请注意。
- 没有地图时才退回：读 `docs/pipeline/PROJECT-BRIEF.md`；两者都没有，才需要自己从代码与前序工单调查业务背景。

## 第一步：先调查，再提问

提问的资格来自调查。逐项完成：

1. **读懂原始需求**：识别业务动机（为什么现在要做）、涉及的业务对象、成功的样子。
2. **先在能力地图上定位，再看代码**：这个需求落在哪条既有能力上？
   - **落在既有能力上** → 那么真正的问题往往不是"要不要做"，而是**扩展它还是新建一个**。带着这个判断去问业务方，而不是让他从零描述；同时读该能力页的"边界与已知问题"——需求碰到已知缺口时必须在 PRD 里显式说明。
   - **跨多条既有能力** → 需求大概率需要拆分，在"关键决策及理由"里给出拆法建议。
   - **不落在任何既有能力上** → 才是真正的新能力；此时反过来查地图"尚不清楚的部分"，确认不是已存在但没被地图收录。
   - 定位之后再用 Grep/Glob 核实代码现状（地图可能落后），记录精确文件路径写进"事实 vs 假设"的事实区。
3. **列出歧义清单，并分清该问谁**：对每个歧义先自答"地图/代码现状/业务惯例是否已经隐含了答案"。
   - 能自答的**不是问题**，写进事实区——每多问一个本可自答的问题，业务方就多一分"我得懂实现才能用这套流程"的负担。
   - 不能自答的分两类：**只有业务方能定的**（业务取舍、优先级、口径）进 open_questions，每条都带推荐答案与依据；**技术实现选择**不进 open_questions，那是计划阶段的事，业务方不该被要求裁决它。
4. **术语核对**（agent 会放大喂给它的词汇歧义，这一步是术语统一的采集点）：需求原文与问答中出现的业务名词逐一对照 `06-glossary.md`——
   - 表里有 → PRD 全程用表内规范词；
   - 表里没有但含义清楚（从代码/上下文可确证）→ 写入 `93-terms.json` 提议新词条；
   - 一个概念有多种叫法或含义存疑 → 先进 open_questions 问清（选项列出候选叫法），确认后再入 `93-terms.json` 并把落选叫法记为禁用同义词。

**第一步完成判据**：In 范围每一项都有「已存在 / 新增 / 与现状矛盾」三选一的调查结论且附文件路径；需求原文每个业务名词都走过术语核对四分支之一。缺任何一项，就还没资格提问或写 PRD。

**提问质量门槛**（不满足就不配出现在 open_questions 里）：
- 答案会实质改变 PRD 或 AC 的内容（问了但怎么答都不影响产物的，删掉）
- 带推荐答案 + 理由（推荐基于调查得出；给不出推荐说明第 1-3 项没做完）
- **必须给选项（≥2 个）**——交互载体是卡片按钮，缺选项回答者就没有否决权；判断型问题至少给「推荐项 + 反向项」

歧义清单非空 → 产出 `10-prd.md` 的**草稿版**（frontmatter `status: NEEDS_CONTEXT`，正文写到当前能确定的程度，"阻塞与开放问题"章列出全部问题），结构化返回带 open_questions，结束本轮。

歧义清单为空（或重跑轮已收齐答案）→ 进入第二步。

## 第二步：产出 PRD + AC 清单

写入 `docs/pipeline/<ticket-id>/10-prd.md`，结构如下（frontmatter 按 handoff-spec §2.1，`stage: clarify`）：

```markdown
## 本阶段结论
[3-5 句：这个需求是什么、边界在哪、几条 AC。审批人只读这一段也能明白。]

## 背景与目标
[业务动机、要解决的问题、成功指标（若业务方给了）]

## 范围
**In：** [逐条列出要做的]
**Out：** [逐条列出明确不做的——防止实现阶段范围蔓延，宁多勿少]

## 需求描述
[逐条功能需求，用业务语言。每条有编号 R-1、R-2……供 AC 反向引用]

## 验收标准（AC 清单）
[格式见下节，每条 AC 标注它验证的 R-n]

## 非功能要求
[性能/兼容/安全等，无则写"无"]

## 关键决策及理由
## 事实 vs 假设
## 失败过的尝试
## 阻塞与开放问题
## 给下一阶段的指令
[通常是：读本文件全文，特别是 Out 范围和 AC 清单；计划的每个任务必须声明覆盖哪些 AC]
```

### AC 编写规则（本 skill 的核心产出，逐条对照）

每条 AC 的固定格式：

```markdown
### AC-3: 子 SKU 继承父级价格覆盖规则（验证 R-2）
**Given** 变体父 SKU 设置了 selling-price overlay
**When** 调用 POST /api/listings/derive-children
**Then** 每个子 SKU 的 price 字段非空且 ≥ 成本价
**业务验收描述：** 从父商品生成子 SKU 后，每个子 SKU 都带着价格，且不低于成本价
**验证方式：** 自动 — `pytest tests/test_derive.py::test_child_price_overlay`
```

- **每条 AC 必须带「业务验收描述」**：一句不含技术词汇的话，业务方读了能独立判断过没过（用户能看到什么/做成什么事）。人工项的验收检查单会直接使用这句话——写不出业务描述的 AC，说明它验证的可能不是需求而是实现细节。

- **每条一个可判定断言**。"功能正常"、"体验良好"不可判定，属于缺陷；一条 AC 里塞多个断言的，拆开。
- **标注"自动 / 人工"**。自动项给出将来能跑的验证命令（测试文件可以尚不存在，但命令和测试名要具体到实现阶段能直接照着建）；人工项给出操作步骤 + 预期看到什么，写到验收人零上下文可执行：
  ```markdown
  **验证方式：** 人工 — 打开商品编辑页 → 选择任一变体父 SKU → 切到"子 SKU 矩阵"标签
  **预期：** 每行子 SKU 的价格列有值且无红色校验错误
  ```
- **覆盖检查**：每条 R-n 至少被一条 AC 验证；每条 In 范围项能指到 R-n。Out 范围不写 AC。
- AC 总数失控（>15 条）通常意味着需求该拆单，在"阻塞与开放问题"里建议拆分并 `DONE_WITH_CONCERNS`。

### 产物二：93-terms.json（新术语提议）

第一步术语核对中确认的新词条，写成 JSON 数组（编排器在工单闭环时发人审卡，通过后入术语表成为全项目用词标准）：

```json
[
  {
    "term": "履约单",
    "definition": "买家付款后系统生成的待发货执行单元，一个订单可拆多个履约单",
    "banned": ["发货单", "出库单"],
    "domain": "订单履约",
    "why": "需求原文与代码注释三种叫法混用，已向业务方确认以「履约单」为准"
  }
]
```

规则：`term`/`definition` 必填且用业务语言；`banned` 列本次澄清中出现过的其他叫法；**没有新术语写 `[]`，不要为了凑数把通用词（用户、列表、页面）当术语**——术语表收的是有业务含义、会被叫错的词。

## 结束

按 handoff-spec §6 自查（特别检查：正文是否混入了实现方案——出现"改哪个函数"、"用什么库"即为越界，改写为行为描述）。然后输出结构化返回（stage-result schema），`summary_for_card` 面向业务方：需求理解成果 + AC 条数 + 新术语提议数 + 请确认什么。

本阶段的 DONE 不代表流程推进——编排器会把 PRD 摘要发飞书卡片等业务方确认，确认通过才进入 pipeline-plan。
